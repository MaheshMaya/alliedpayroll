Status: slice 1 delivered 2026-11-22 (read-only users and roles, real permissions; `/me` deferred to slice 7 since bootstrap already carries the person). Slice 2 delivered 2026-11-22 (audit trail: `AuditSink` port, security listeners, partition upkeep on batch, Settings → Audit log; the generic entity listener and the actor/entity filters in the UI wait for the first PII entities). Slice 4 delivered 2026-11-22 (profile packs `profiles/{CODE}.vN.json` reconciled into `industry_profile_template` and immutable once published; provisioning adds the profile's `module:*` flags the tenant has no row for, also for tenants that already exist; Settings → Modules and Settings → Terminology; bootstrap carries `terminology` in the request's language; the web names nav groups and the client chip through `useTerms()`). Deviations: profile labels are not copied into `terminology_override`; they are a layer under the tenant's own labels (LOCALIZATION_I18N §5), so a newer profile version reaches tenants that never relabelled; the resources are `/api/v1/modules/{code}` and `/api/v1/terminology/{locale}` (one save per language) instead of `feature-flags/{flagKey}` and one PUT per concept; number-series seeds move to slice 5 with the number-series screen; the role codes stay the identity catalogue for every profile; `listIndustryProfileTemplates`, the bootstrap ETag and `If-None-Match` are not built (the web refetches the bootstrap after a change). Slices 5 to 9 remain proposals. Scope is DEVELOPMENT_PLAN.md §4 Phase 1 (backend, web rows); the mobile row is being built separately and is marked "mobile slice later" here. Every slice follows the `vertical-slice` skill: backend API and web screen built together, proven through the real OIDC login (`/auth/login` → Keycloak → `/auth/callback`) as a seeded tenant user on the tenant subdomain. No auth bypass anywhere.

## 2. Cross-cutting design (done inside slice 1 and 2, used by all)

- **Module dependency direction.** `identity` → `tenant.api` (listens to `TenantProvisioned`); `tenant` never depends on `identity`. `BootstrapUseCase` keeps reading user facts from `AuthenticatedUser`. Modulith verification (`ModulithStructureTest`) enforces it.
- **`PrincipalEnricher` port** in `common-security` (`TenantPrincipal(userId, status, roles, permissions, DataScope)`), default no-op bean, implemented by `identity.infrastructure.security.PrincipalEnricherAdapter` (Caffeine cache keyed by tenant+subject, evicted on `RoleChanged`/`UserDisabled`). `CurrentUserProvider.fromJwt/fromSession` call it; `AuthenticatedUser` gains `@Nullable UUID userId`, `DataScope scope`.
- **`DataScope`** value object in `common-security` (`mode ALL|RESTRICTED`, sets of legalEntityIds, branchIds, clientIds, siteIds) and a `DataScopePredicates` helper. Phase 1 only stores and surfaces it; referents (`organization.*`, `customer_contract.*`) and the query-layer predicates arrive with Phases 2 and 3.
- **`AuditSink` port** (`record(AuditEntry)`) in `common-core`, implemented by the audit module; `common-security` writes `LOGIN`, `LOGIN_FAILED`, `LOGOUT`, `AUTHZ_DENIED` from Spring Security events; use cases call `record(...)` explicitly with masked values. A generic Hibernate listener is Phase 2 work (first PII entities).
- **Permission catalogue is code.** Each module declares a `PermissionCatalogue` contributor (`identity:users_read`, `identity:users_manage`, `identity:roles_manage`, `identity:devices_manage`, `identity:help_requests_read`, `tenant:settings_manage`, `tenant:branding_manage`, `audit:read`, `audit:security_read`); the identity startup reconciler upserts `identity.permission`.
- **Default roles** are an identity-owned catalogue (`TENANT_ADMIN`, `PAYROLL`, `HR`, `SUPERVISOR`, `EMPLOYEE`, `CLIENT_CONTACT`), copied as `system = true` roles when `TenantProvisioned` arrives; the profile template payload lists which role codes a profile gets (data, not `if (industry…)`).
- **Seed.** `DemoTenantSeeder` (`backend/app`) also calls `identity.api.UserAdministration.ensureUser(...)` for the 7 Keycloak users with roles: `admin.*` → TENANT_ADMIN, `payroll.*` → PAYROLL, `hr.sentinel` → HR, `guard.sentinel`/`staff.nimbus` → EMPLOYEE. Playwright personas: `admin.sentinel` (everything), `guard.sentinel` (403 cases), `admin.nimbus` (isolation).
- **Bootstrap grows** to `Bootstrap(tenant, user{id,subject,displayName,email,status,roles,scopeMode,preferredLocale}, permissions, features, branding, terminology{bundleVersion, labels}, settingsPublic)` with an `ETag` from the latest `updated_at` across tenant tables; `MobileBootstrap` adds `appPolicy{minSupportedVersion, latestVersion}`. Additive only; the SDK is regenerated per slice.
- **Flyway.** `application.yml` `spring.flyway.locations` gets `classpath:db/migration/identity` and `classpath:db/migration/audit`; `spring.messages.basename` gets `i18n/identity/messages,i18n/audit/messages`. `settings.gradle.kts` adds `modules:identity`, `modules:audit`; `backend/app/build.gradle.kts` depends on them.

## 3. Slices, in order

Estimates are pair-days (one backend + one web engineer). Total about 39 pair-days; with three streams in parallel it fits the two sprints. The order is fixed by dependencies: permissions first, audit before the first write slice, templates before settings, branding before the shell polish.

### Slice 1 (first): Users and roles, read-only, with real permissions — 5 days

- **User-visible outcome.** `admin.sentinel` opens Settings → Users and sees the four Sentinel users with their roles and status; `guard.sentinel` sees the Settings entry hidden and gets 403 from the API; nothing of Nimbus is visible.
- **Backend.** New module `backend/modules/identity` (`@ApplicationModule`, packages api/web/application/domain/infrastructure). `V2_1__identity.sql` lifted from docs/schema/identity.md §3 (all tables except `otp_challenge`; grants as in `V1_1__tenant.sql`). Entities `AppUserEntity`, `RoleEntity`, `RolePermissionEntity`, `UserRoleEntity`, `DataScopeEntity`, `PermissionEntity` (platform-owned, no `@TenantId`). Permission reconciler. `TenantProvisioned` event record in `tenant.api` published by `ProvisionTenantUseCase`; identity `@ApplicationModuleListener` creates the system roles (idempotent through `ProcessedEvents`). `PrincipalEnricher` port + adapter (§2). JIT link: on first authenticated request where `keycloak_subject` is null and `username` matches, set subject, `status = ACTIVE`, `activated_at`, publish `UserActivated` (audited in slice 2). Endpoints: `GET /api/v1/users` (`listUsers`, page/size, `filter[status]`, `q`, `identity:users_read`), `GET /api/v1/users/{id}` (`getUser`, ETag), `GET /api/v1/roles` (`listRoles`), `GET /api/v1/roles/{id}` (`getRole`, with permission codes), `GET /api/v1/permissions` (`listPermissions`, grouped by module), `GET /api/v1/me` (`getMe`). Events: `TenantProvisioned`, `UserActivated`.
- **Web.** Route group `routes/settings/` with `settings.tsx` layout (sub-nav) and `settings/users.tsx`; `features/settings/users/users-page.tsx` (TanStack Table, status Badge, role chips, masked email/phone), `user-detail-drawer.tsx` (read-only). `nav-config.ts`: `to` type widened to the route union, `settingsNav.to = "/settings/users"`, `permission?: string` on `NavLeaf` and `visibleNav` filters on `bootstrap.permissions`. SDK: `listUsers`, `getUser`, `listRoles`, `getMe`. A `useHasPermission()` hook over `useBootstrap()`.
- **Tests.** Unit: permission catalogue reconciler, role-template copy, `PrincipalEnricher` cache eviction, `visibleNav` by permission. Testcontainers: `@ApplicationModuleTest` for identity (migration, event listener), `IdentityRlsTest` modelled on `RowLevelSecurityTest` for `app_user` and `role`; cross-tenant read/update/delete as `nimbus-it`; per-tenant uniqueness of `role.code`. API: `UsersAuthorizationTest` (guard → 403 problem code `authz.denied`; nimbus token on sentinel host → 403). Playwright `e2e/settings-users.spec.ts`: sign in as `admin.sentinel`, open Settings → Users, assert 4 rows; as `guard.sentinel` the nav entry is absent and `/settings/users` shows the no-access state; storage state saved once per worker (`e2e/auth.setup.ts`).

- **Outcome.** Settings → Devices lists registered app installs and kiosks (empty state until the app ships) with remote disable; the admin sets the minimum supported app version and `GET /api/v1/mobile/bootstrap` returns it.
- **Backend.** `DeviceEntity`, `DeviceCredentialEntity`, `KioskEnrolmentEntity` (tables exist from slice 1). `identity.api.DeviceRegistry` (register, touch, disable). mobile-channel: `POST /api/v1/mobile/devices` (`registerDevice`, Idempotency-Key, install-id HMAC, binds to the caller) → `DeviceRegistered`; `MobileBootstrapController` adds `appPolicy` from `TenantSettings` (`MOBILE.min_supported_version`, `latest_version`) and `device` echo. Web endpoints: `GET /api/v1/devices` (`listDevices`), `POST /api/v1/devices/{id}/disable` (`disableDevice`) → `DeviceDisabled`. Kiosk enrolment (`POST /api/v1/kiosk-enrolments`, `createKioskEnrolment`) needs `work_location` → Phase 2; contract only, returns 422 `identity.work_location_required` until then.
- **Mobile slice later.** OTP sign in (D1), PKCE, device-bound refresh token, biometric unlock, forced-upgrade screen, kiosk QR scan: planned with the Flutter scaffold; the contracts above are what it consumes.
- **Web.** `routes/settings/devices.tsx` (list, disable with reason), min-version fields live on Settings → General (slice 5).
- **Tests.** Unit: install-id hashing, `ck_device_binding` mirrored in the aggregate. Testcontainers: RLS on `device`; `registerDevice` replay is idempotent. API: `registerDevice` with a WEB-channel session is refused (channel policy); 403 on `disableDevice` for `hr.sentinel`. Playwright `e2e/devices.spec.ts`: empty state, then the min-version round trip via `getMobileBootstrap` (registering a device from Playwright would need a mobile-channel JWT, which no bypass may mint).

## 4. Risks

| Risk | Mitigation |
|---|---|
| Keycloak 26 Organizations has no per-organisation login theme, so tenant branding on the IdP page is limited | Render the neutral Allied theme on the IdP page and apply tenant branding after sign-in; fetching `GET /api/v1/branding` anonymously from the theme is not acceptable. Note it in the usability round. |

| Anonymous endpoint under `/api/**` | Exactly one path+method `permitAll`, tenant required, Redis rate limit, no PII echo, covered by `BootstrapIsolationTest`-style negative tests. |
| Data scopes without referents in Phase 1 | Stored and shown only; `DataScopePredicates` has tests but no callers until Phase 2. Do not fake a legal-entity list. |
| Keycloak Admin API coupling and flakiness | Port + adapter, timeouts, idempotent create (lookup by username first), failures leave the user `INVITED` with `last_sync_error`, nightly reconcile. |
| Audit partition drift | Default partition + alert; batch job creates three months ahead; tested in slice 2. |
| OpenAPI churn across 9 slices | Each slice regenerates the SDK (`pnpm api:generate`) in the same PR; additive only; `OpenApiExportTest` diff is the review. |
| `e2e/login.spec.ts` asserts Keycloak's stock login page | D2's theme must keep the `username`/`password` labels and "Sign in" button names, or update the spec in the same PR. |
